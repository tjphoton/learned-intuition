sbi: A Toolkit for Simulation-Based Inference

Tejero-Cantero, Boelts, Deistler, et al.·2020·JOSS
Open PDF (private repo) Back to study plan
Summary

The other major SBI library (Macke lab, PyTorch). Lower-level than BayesFlow — exposes the density-estimator choice directly (NPE / NLE / NRE families) instead of one high-level API.

Study Notes

This is where SNPE / SNLE / SNRE are actually named — a correction owed to cranmer.html

Earlier in this reading order, an early pass through Cranmer et al. mistakenly attributed the acronyms NPE/NLE/NRE and the SNPE-A/B/C leakage-bug history directly to that paper — later corrected once the actual PNAS text was checked and found not to contain them. This toolkit paper is where that history is genuinely, correctly documented: sbi implements three families by name — Sequential Neural Posterior Estimation (SNPE), specifically SNPE-C (Greenberg, Nonnenmacher & Macke's "Automatic Posterior Transformation," 2019 — the fix for the earlier SNPE-A leakage problem); Sequential Neural Likelihood (SNLE) (Papamakarios, Sterratt & Murray, 2019); and Sequential Neural Ratio Estimation (SNRE) (Hermans, Begy & Louppe, 2020, plus a contrastive-learning variant from Durkan, Murray & Papamakarios). The "sequential" leakage-and-fix history is real — it just belongs here, not in Cranmer's 2020 survey.

A brief but real lineage: delfi → lfi → sbi

sbi succeeds delfi (Mackelab's earlier package, built on Theano — discontinued once Theano itself was discontinued as a project). The sbi codebase itself started as a fork of lfi, developed by Conor Durkan. It's closely integrated with PyTorch and uses nflows (Durkan, Bekasov, Papamakarios & Murray) for its flow-based density estimation.

What sbi actually returns: a NeuralPosterior object

The inference step returns a NeuralPosterior object exposing the same API surface as a standard PyTorch probability distribution — sample from it, and (if the chosen algorithm supports density evaluation — recall not all three families do equally cheaply) evaluate its density directly. A deliberately familiar interface for anyone who already works in PyTorch.

Practical engineering for messy, pre-existing simulators

Works with any simulator that can be wrapped in a plain Python callable — handles automatic shape inference, input standardization, and failed-simulation handling so users don't have to write that plumbing themselves. Leverages vectorization and optional joblib-based parallelization to maximize simulator throughput, and supports an optional trainable summarizing network for dimensionality reduction, sparing users manual feature engineering — the same "let a network find the summary statistics" idea covered conceptually in Zammit-Mangion et al.

Two interface levels — a genuine usability design choice

A full-featured interface (custom networks, tunable hyperparameters) for researchers who want control, and a deliberately separate simple interface — a single function call with reasonable defaults — specifically so new users can get a working result before learning to define custom networks or tune anything. Worth noting since it's the same "novice-friendly default path" goal NPE-PFN pursues by a completely different route (borrowing a pretrained tabular model instead of shipping good defaults for a from-scratch training pipeline).

Related software, per the paper's own account (Sec. 1.1)

  • elfi — offers BOLFI (a Gaussian-process-based algorithm) plus classical ABC methods.
  • carl — implements one specific calibrated-classifier likelihood-ratio algorithm.
  • hypothesis, pydelfi — two other SBI packages, under development at time of writing.
  • pyabc, ABCpy — packages offering a diversity of classical ABC algorithms specifically, not neural methods.
Discussion, Section by Section

Plain-English walkthrough (start here)

Builds on cranmer.html's three-way surrogate taxonomy (learn the posterior, the likelihood, or the ratio) — this paper is one of the two libraries (with BayesFlow) that actually implements all three as installable, documented code.

1. Why the "sequential" acronyms matter, and why getting their origin right matters too

Each of the three families this library implements has a "sequential" refinement version, and it's genuinely useful to know that history exists — a first sequential posterior method had a real bug (probability could leak outside where it was supposed to live), and it took a specific, citable follow-up paper to fix it properly. What matters for how you read this whole field: a fast neural method being published doesn't mean it's already been fully debugged — that's a pattern worth watching for repeatedly, not a one-off historical curiosity.

2. A library that hands you the parts, not a finished machine

Where BayesFlow leans toward "here's a sensible default pipeline, customize if you need to," sbi leans the other way: pick your family (posterior, likelihood, or ratio), pick sequential or not, and the library gives you the pieces. That's not better or worse — it's a different bet about who's using it and how much they already know about their own problem.

3. Two doors into the same house

A brand-new user can call one function with sensible defaults and get a working result immediately — no need to understand summary networks or normalizing flows first. An experienced researcher can go in through the other door and control every architectural choice. Worth noticing as a genuinely deliberate design decision, not an accident: the same underlying machinery serves both audiences without forcing either to learn the other's workflow first.

Going deeper (revisit once the basics above feel solid)

Worth explicitly re-checking the amortization-vs-sequential framing from bayesflow2.html's own self-comparison once this page is fresh: BayesFlow 2 describes itself as amortization-first while crediting sbi with "native support for non-amortized methods such as sequential and multi-round posterior, likelihood, and ratio estimation." This paper's own description (three sequential families, by name, as a headline feature) matches that framing closely — a rare case in this library of two papers' mutual self-descriptions actually lining up cleanly.
